C-017: how the candidate was eliminated

Two runs of the same decision. Task, evidence set and model held fixed; the only intended difference is whether a previously committed resolution was treated as binding.

In Run A the resolution is available as retrieved context, and the model produces provider_a. In Run B the same resolution is binding, and the candidate set is filtered before an answer is accepted.

Elimination trace

The comparison below is performed by a deterministic kernel, not by the model. Each eliminated candidate carries the value that was tested, the operator and threshold it was tested against, and the resolution responsible for the elimination.

The model does not get to weigh the earlier resolution more or less heavily. In Run B an output naming provider_a is not accepted, regardless of what the model proposes.

What this shows, and what it does not

It does not prove that provider_b is the correct decision.

It does not establish that binding historical resolutions improve decision quality in general.

It shows that a committed resolution can constrain the set of decisions available later, by removing options rather than by being retrieved as context.

On publication

This page reports an experiment. The canonical record of the run, its cryptographic seal, and an independent verification path are a separate release. They are not published yet, and nothing on this page should be read as a verified artifact. When that release lands, the record will be verifiable without trusting this site.

The ISCProof specification and its verifier cover the integrity of sealed packs. Integrity is not the claim being made here.
