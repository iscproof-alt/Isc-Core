Verifiable decision records

When a decision is questioned, show the record.
And show it hasn’t changed since it was signed.

ISC packages decision records and their recorded inputs, policy versions or references into signed evidence files. Download the example and check its file hashes and manifest signature on your own machine.

A record of what was captured—not proof that it was true.

Verification checks the packaged files against a signed manifest. It does not establish that the recorded policy was in force, that the inputs were accurate or that the decision was correct. This demonstration includes no independently verified signing or creation time.

ILLUSTRATIVE SCENARIO · REAL SIGNED FILES

Same request. Different recorded limits. Different decisions.

A request for 3,000 is approved under a limit of 5,000. The limit changes to 2,000; the same request is then rejected. These are demonstration records, not customer data or a live AI execution.

The verifier checks the signed manifest and file hashes. This example does not test decision correctness or enforce the meaning of the links between records.

Verification scope

Know what was checked.

ISC checks in this example

  • Whether the listed files match their manifest hashes.
  • Whether the manifest signature verifies against the explicitly supplied demo signer key.
  • Acceptance and rejection in the five published test cases: valid, changed-content, missing-file, missing-signature and rewritten-manifest.

ISC does not check in this example

  • Whether the recorded facts are accurate or a policy was actually in force.
  • Whether a decision was correct or justified.
  • The meaning or validity of relationships between records.
  • When the package was created or signed. Dates inside the files are signer-stated, not independently timestamped.

No RFC 3161 timestamp or blockchain anchor is included. The demo key identifies this demonstration; it does not independently establish the issuer’s identity. The TAR archive SHA-256 shown below is a separate download checksum, not the verifier’s internal package-identity calculation.

Download and verify

Check the package on your own machine.

The kit includes the evidence archive, demo signer list, exact verifier source snapshot, records and internal test outputs.

Linux x86-64 verifierComplete verification kitEvidence packageDemo signer list

Prebuilt binary: Linux x86-64, dynamically linked; requires glibc 2.34 or later and compatible system libraries. It is not a Windows or macOS executable.

Run the Linux binary

Place the binary, evidence package and signer list in the same directory. Then run:

chmod +x isc_verify-linux-x86_64
./isc_verify-linux-x86_64 evidence_pack.tar --trusted-signers trusted_signers
Build from source instead

Unzip the kit. With Rust and Cargo installed:

cargo build --release --locked --manifest-path verifier-source/Cargo.toml
./verifier-source/target/release/isc_verify evidence_pack.tar --trusted-signers trusted_signers

Building from source with --locked avoids relying on the prebuilt executable. You still trust the source, compiler and dependencies; --locked preserves dependency resolution, not a guarantee of correctness or reproducible binary output.

This website supplies both the files and demo key. For evidence from another issuer, obtain the expected signer key through a channel you trust. A checksum from this same website detects a changed download against the published value; it is not an independent trust source.

Where it fits

A format for records you may need to examine later.

Decision records

Can carry a recorded outcome, reasons and policy version.

Agent records

Can carry references to recorded instructions, inputs and tool outputs.

Review packages

Can carry files and verification material for another party to inspect.

These describe possible uses of the format, not independently validated deployments. This demonstration tests file hashes and a manifest signature.
